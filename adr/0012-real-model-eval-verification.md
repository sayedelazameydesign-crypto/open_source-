# ADR-0012: تشغيل التقييم بنموذج حقيقي — تحقق فعلي وإصلاح إشارة كاذبة

**التاريخ:** 2026-10-14 · **الحالة:** مقبول ومُنفَّذ (فوق ADR-0011)

## السياق

أمر التشغيل الواحد للتقييم بنموذج حقيقي عبر بوابة خاصة (OpenAI-compatible):

```bash
pip install -e ".[dev,server]"
CELA_EVAL_API_KEY="<token>" python -m os_evals run --suite builtin \
  --model-url https://gateway.example.com/v1 --model-id <model> \
  --auth-header Authorization --api-key-env CELA_EVAL_API_KEY \
  --out eval-report.json --ab-skills
```

قيمة المفتاح سر لا يصل إلى جلسة التطوير، والبوابة الخارجية غير قابلة للوصول من
هنا، لذلك شُغِّل **المسار البرمجي نفسه** مقابل بوابة `OpenAI-compatible` محلية
(stub) تحاكي العقد بدقة: ترويسة مصادقة، وطلب أداة `python_execute` في الجولة
الأولى، ثم جواب نهائي **بصياغة نموذج حقيقي** لا بصياغة سكربت العرض.

## ما شُغِّل فعلًا (سجل التحقق)

| الفحص | النتيجة |
|---|---|
| مفتاح خاطئ + `--ab-skills` | خروج `2` ورسالة «every case in both arms errored»، والتقرير مكتوب للمعاينة |
| `--auth-header x-api-key` | يمرّ عبر الترويسة الصحيحة (بلا `authorization`) |
| دورة أداة كاملة: طلب `python_execute` ثم جواب نهائي | نجحت؛ طلبان لكل حالة، والتوكنز مسجّلة من `usage` (771 للذراع) |
| طلبات وصلت البوابة في تشغيل A/B كامل | 8 = حالتان × ذراعان × جولتان |
| التقرير لا يحوي قيمة المفتاح | مُثبَت (نفس فحص ADR-0011) |
| `--suite builtin` دون نموذج (منصة العرض) | 2/2 كما قبل التغيير |

## العيب المُكتشَف: فحص بشكل السكربت لا بشكل الجواب

`builtin-answer-shape` كان يثبّت جملة منصة العرض حرفيًا:
`sum of 0\.\.100 is 5050`. نموذج حقيقي أجاب — بعد تنفيذ فعلي في الصندوق —
«The sum of the integers from 0 to 100 is 5050.» أي **جواب صحيح 100%**، فأسقطه
الفحص: نسبة نجاح `0.5` لسكربت صحيح، وخروج `1` في تشغيل مفرد، ولوحة A/B
تبرّئ المهارات من ذنب لم تقترفه. لم يتوقف الأمر عند نسبة النجاح: الوسيط
`false_injection_rate_proxy` قفز إلى `1.0` بدل `0.0` لأن الحالة الوحيدة التي
حملت مهارة محقونة هي الحالة التي أسقطها الفحص.

**قاعدة الإصلاح:** الفحص يجب أن يقيس **محتوى الجواب** لا **صياغته**.

1. `builtin-answer-shape` صار: `(?is)\bsum\b.*?\b0\b.*?\b100\b.*?\b5050\b`
   — المجموع، ثم المدى، ثم الناتج، بهذا الترتيب. يقبل جملة العرض *وأي* صياغة
   صحيحة، ويرفض ناتجًا خاطئًا (`4950`) أو غياب الجواب. توثيقه داخل `suites.py`
   بأنه فحص نموذج-محايد إلزاميًا.
2. ملاحظة على `stderr` عند `--suite builtin` مع `--model-url`: هذه المجموعة
   **فحص توصيل من حالتين وليست مقياس جودة**؛ الأرقام المنشورة تحتاج
   `--dataset`. الـ`stdout` يبقى JSON صافيًا للتوجيه إلى ملف.
3. التشغيل المفرد كان ينهار بصمت عند فشل **كل** الحالات (مفتاح غير محقون):
   خروج `1` بلا كلمة. الآن تُطبع رسالة تسمّي `$<api_key_env>` — نفس معالجة
   مسار A/B في ADR-0011.

## عقد رموز الخروج (وثيقة دائمة)

| الأمر | `0` | `1` | `2` |
|---|---|---|---|
| تشغيل مفرد | كل الحالات نجحت | حالة فشلت (وشملها انهيار الكل + تشخيص) | — |
| `--ab-skills` | **لا تراجع** من المهارات (ليس «كل الحالات نجحت») | تراجع | لا قياس: كل الحالات انهارت في الذراعين |

التقرير يُكتب **قبل** أي رمز خروج، فيبقى الدليل على القرص قابلاً للفحص.

## ما ينقص للتشغيل الفعلي

* من المالك: النموذج والوجهة محفوظان كأسرار (`CELA_MODEL_BASE_URL` و
  `CELA_MODEL_ID`) — لا كمدخلات حرة — والسر `APIDOG_ACCESS_TOKEN` يمرّ في
  مسار واحد: secret ← متغيّر بيئة ← عميل النموذج. **تدعيم أمني
  (2026-10-16):** الوجهة صارت مثبّتة على السر وحده (أُزيل مدخل `model_url`
  الحر الذي كان يسمح بإرسال الرمز إلى أي مضيف يُدخله المشغّل)، وقاطع
  `ALLOW_LIVE_EXTERNAL_CALLS=true` مطلوب قبل أي طلب مدفوع، والمسار يُعاد
  التحقق منه داخل العدّاد أيضًا. الاختبار الحارس: `tests/test_eval_workflow_security.py`.
* أرقام منشورة تحتاج `--dataset` بصيغة GAIA/SWE-bench، لا `--suite builtin`
  (راجع البوابة 2 في `docs/ROADMAP.md`).
* الاختبارات: `tests/test_evals.py` يغطي الآن صياغة النموذج الحقيقي، وتشغيل
  CLI كامل بنموذج موقوفًا محل النموذج الحقيقي، ورسالة الانهيار الكامل — دون شبكة.
