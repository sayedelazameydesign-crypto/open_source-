# ADR-0001: التنفيذ المعزول عبر Backend قابل للاستبدال بدل Docker المباشر

**التاريخ:** 2026-10-09 · **الحالة:** مقبول

## السياق
وثيقة التصميم تشترط E2B أو Firecracker بدل "Docker التلقائي" لضمان العزل. لكن النموذج
الأولي يجب أن يعمل على أي جهاز تطوير دون بنية سحابية، ودون أن يُضحّى بالعقد الأمني.

## القرار
تعريف `CodeExecBackend` كـ Protocol بطرف واحد:

```python
async def execute(self, code, *, language, files, timeout) -> ToolResult
```

مع تنفيذين:

* `LocalSubprocessBackend` — العملية الفعلية الآن: `setrlimit` + مهلة wall-clock +
  `cwd` مؤقت + `unshare --net` عند توفره.
* `InMemoryBackend` — استجابات مُعلَّبة للاختبارات الحتمية.

## النتائج
* ✅ الوكلاء لا يعرفون أي شيء عن backend؛ استبدال E2B/Firecracker تغيير في ملف واحد.
* ✅ الاختبارات تُنفِّذ الكود الحقيقي دون حاويات ولا شبكة.
* ⚠️ **العزل المحلي جزئي صراحةً:** `unshare` يتطلب Linux + صلاحيات. عند غيابه يُبلَّغ
  `network="unverified"` ولا يُدَّعى العزل. هذا قيد مُعلن، لا ثغرة مخفية.
* ⚠️ لا يوجد عزل ملفات على مستوى kernel محليًا؛ `RLIMIT_FSIZE` و`cwd` المؤقت تخفيف لا
  منع. الإنتاج يجب أن يستخدم microVM.

## بدائل مرفوضة
* **Docker لكل استدعاء:** زمن إقلاع ~300ms لكل خطوة، وتعقيد نشر، ولا يمنع
  microVM escape أفضل من rlimits بشكل جوهري.
* **`exec()` في العملية:** مرفوض قطعًا — لا عزل إطلاقًا، و`RLIMIT` لا ينطبق على
  العملية الأم.
