## 1. معنى تصنيف الأدلة

- **VERIFIED — code:** حقيقة قُرئت في الرمز، لا نتيجة تشغيل أو تحليل صفوف قاعدة فعلية.
- **VERIFIED — filesystem:** وجود ملف وحجمه عبر metadata فقط، دون قراءة محتواه.
- **VERIFIED — upstream source:** سلوك موصوف في مصدر SQLite الرسمي المشار إليه أدناه.
- **NOT VERIFIED:** حالة تشغيل أو محتويات أو إعداد فعلي لم يُفحص، أو سياسة لم تُنفذ.
- **BLOCKED:** قرار أو ضمان لا يجوز إغلاقه بالأدلة المتاحة؛ ليس تصريحًا بفشل اختبار.

نتائج المتصفح السابقة محفوظة في [تقريرها](MVP_0_BROWSER_VERIFICATION.md)، لكنها لا

## 3. تدفق البيانات الحالي — VERIFIED من الكود

```text
قرص المستخدم: TXT الأصلي (خارج ملكية التطبيق)
    ↓ اختيار الملف
المتصفح: File + اسم محلي في حقل الاختيار/React state
    ↓ POST /api/backend/document-runs?filename=... ؛ جسم الملف مباشرة
Next: تدفق جسم الطلب + query، ورمز المنصة من بيئة الخادم
    ↓ POST /document-runs?filename=...
FastAPI: bytearray → bytes → str بعد UTF-8 الصارم
    ↓ التحقق قبل إنشاء المهمة
RunState.metadata = {source: النص الكامل, size_bytes, events, document_status}
    ↓ save_state عند كل انتقال
SQLite إن اختيرت:
  run_states.state_json: النص الكامل داخل metadata.source
  run_meta: المعرّف، mode، status، created_at؛ بلا نص المستند
  WAL: قد يحمل إصدارات صفحات متعاقبة لهذه الكتابات
أو InMemoryRunStore الافتراضي: كائن الحالة في RAM فقط
    ↓ تأكيد تنفيذ صريح
render_report: bytes UTF-8 لتقرير يحوي مقتطفًا وإحصاءات ومعرّفًا وتوقيتًا
    ↓ save_artifact
run_artifacts.data_json: content كامل + artifact_id + size_bytes + sha256 + mime_type
    ↓ حذف source من الحالة الحالية ثم save_state
run_states.state_json: أحداث وإحصاءات وبيانات Artifact وبصمته؛ بلا نص التقرير نفسه
    ↓ مسارات متعددة لاسترجاع Artifact
HTTP bytes عبر download أو JSON يحوي content عبر المسارات المشتركة
    ↓ تنزيل المستخدم
ملف Markdown على جهاز المستخدم (نسخة خارج ضمان حذف التطبيق)
```

**الإجابة المباشرة عن الازدواج:** المصدر الكامل يُحفظ في **سجل الحالة** وليس Artifact
إدخال. التقرير والمقتطف يُحفظان في **Artifact**؛ الحالة تحفظ مؤشر التقرير وبصمته
وإحصاءاته لا content. أثناء التنفيذ توجد نسخ RAM لكليهما، وقد تبقى نسخ صفحات تاريخية
في SQLite/WAL. الخطة `_PLAN` ثابتة في الكود وتُعاد عند القراءة، وليست وثيقة خطة مستقلة
داخل SQLite. أحداث المستندات داخل `metadata.events`، وليست مسار EventBus المعتاد.

### ملفات قاعدة فعلية رُصدت دون فتحها

فُحصت metadata تحت `.cela/` و`.cache/` فقط. وُجدت:

| الملف | الحجم بالبايت | التصنيف |
|---|---:|---|
| `.cela/mvp0-verification.db` | 2,142,208 | VERIFIED — filesystem |
| `.cela/mvp0-verification.db-wal` | 5,421,952 | VERIFIED — filesystem |
| `.cela/mvp0-verification.db-shm` | 32,768 | VERIFIED — filesystem |

هذه أسماء ملفات تحقق قديم؛ **لم تُقرأ صفوفها أو محتوياتها، ولم تُحذف**. لا يُستنتج من
اسمها أن محتواها آمن، أو أن إزالة source حدثت فيها. الملف WAL أكبر من DB مثال مرصود
على أن حجم القرص ليس حجم المحتوى المنطقي. هذا جرد للمسارين المذكورين، لا مسح شامل
لكل الأقراص أو حسابات الاستضافة. متغير `CELA_RUN_STORE_URL` غير مضبوط في بيئة أمر
الفحص؛ لا يثبت ذلك إعداد تطبيق آخر، فقد يُمرَّر store_url صراحة. الافتراضي البرمجي
ذاكرة، وSQLite مكانها هو المسار الذي يختاره الإعداد، وليس اسمًا ثابتًا يفرضه التطبيق.

## 5. السلوك الحالي عند الانتقالات والانقطاع

| الحالة | ما يثبته الكود الآن | التصنيف/الفجوة |
|---|---|---|
| طلب مرفوض قبل الإنشاء | التحقق يسبق RunState؛ لا ينشأ صف مصدر لهذا الطلب عبر D2؛ الاسم قد يدخل access log | VERIFIED — code؛ لا إثبات محو RAM |
| انتظار التأكيد | المصدر الكامل باقٍ في الحالة؛ لا فحص 24h في load/execute | VERIFIED — code؛ انتهاء الصلاحية NOT VERIFIED/غير منفذ |
| RUNNING | المصدر يحفظ عند الانتقال قبل try؛ إعادة execute تعيد RUNNING بلا عمل جديد | VERIFIED — code؛ لا مهلة لاستعادة RUNNING المتروكة |
| نجاح طبيعي | حذف source من نسخة الحالة ثم save_state؛ التقرير باقٍ في Artifact | VERIFIED — code؛ ليس محوًا من WAL أو cache قديم |
| فشل المعالجة داخل try | إزالة source ومؤشر Artifact وخطأ عام، ثم حفظ FAILED | VERIFIED — code؛ لا delete لصف Artifact سبق أن حُفظ |
| فشل حفظ/قرص أو crash | حفظ Artifact وحفظ الحالة ليسا معاملة واحدة؛ يمكن بقاء source أو Artifact يتيم إذا انقطعت السلسلة | VERIFIED — code لخطر ترتيب العمليات؛ حدوثه فعليًا NOT VERIFIED |
| إلغاء المستخدم | RunStatus.CANCELLED موجود في الطبقة المشتركة؛ لا مسار إلغاء أو تنظيف مستندات في Router | VERIFIED — code؛ لا ضمان حذف عند الإلغاء الآن |
| تجاوز عمر التقرير/المهمة | لا TTL ولا منظف ولا حصة إجمالية؛ الموجود حد 1 MiB لكل ملف فقط | VERIFIED — code؛ 7d/30d/100 MiB غير منفذة |
| إعادة التطبيق بـSQLite نفسها | يمكن إعادة تحميل state وArtifact؛ لا sweep عند startup أو load | VERIFIED — code؛ الاختبارات السابقة دليل مسجل لا إعادة تحقق في الجولة الحالية |
| إعادة التطبيق بمخزن RAM | لا استمرارية؛ زوال مراجع العملية لا يثبت المحو المادي | VERIFIED — code |

تفصيل مهم: SQLite يعيد كائنًا جديدًا عند get_state. قد تحتفظ `ApiRuntime.states`
بنسخة **سابقة** للمصدر إذا قُرئت لقطة عامة أثناء الانتظار، بينما يعالج DocumentRuns
نسخة أخرى لاحقًا. snapshot لا يُخرج metadata إلى العميل، لكن عدم إخراجها لا يساوي
إزالتها من RAM. يلزم اختبار cache وإبطاله، لا تحديث صف SQLite وحده.

`finished_at` لا يُملأ في مسار المستندات الحالي لأنه لا يستدعي mark_finished.
والتقرير يطبع started_at للمهمة، ولا توجد artifact_created_at مستقلة. لا يجوز تنفيذ
سياسة 7 أيام اعتمادًا على التوقيت المطبوع باعتباره وقت إنشاء التقرير الفعلي دون قرار
صريح للبيانات القديمة.

## 6. جميع منافذ الوصول التي يجب أن يطالها انتهاء الصلاحية

1. `GET /document-runs/{id}` و`POST /document-runs/{id}/execute`.
2. `GET /document-runs/{id}/artifacts/{artifact_id}/download`.
3. `GET /artifacts/{run_id}/{filename}`: يعيد JSON الكامل، ومنه `content` للمستند.
4. `GET /cela/v1/runs/{run_id}/artifacts` و`.../artifacts/{filename}`:
   القائمة والاسترجاع يعيدان محتوى Artifact عبر السطح الخاص إذا كانت مصادقته مهيأة.
5. لقطات/قوائم المنصة والسطح الخاص وأي runtime/store cache، إضافة إلى تذاكر الوصول
   والأحداث المشتركة المرتبطة بمعرّف المستند.
6. وكيل Next يعيد هذه المسارات ولا يطبق TTL مستقلًا؛ no-store ليس آلية حذف.

وجود المصادقة لا يعفي المسارات المشتركة من الاحتفاظ. **حجب download وحده يترك منافذ
JSON للمحتوى.** المقترح فرض صلاحية محتوى المستند عند نقطة مشتركة تشمل get/list/cache،
مع الحفاظ على عقود مهام الوكيل غير المستندية. لا يُغيّر ذلك هنا، ولا توجد شهادة بأن
السياسة مطبقة حاليًا.

## 7. عقد الاحتفاظ المقترح للاعتماد — غير منفذ

### 7.1 الزمن والحالات

- الزمن UTC ومقارنات زمنية صريحة؛ `now >= expires_at` يعني منتهيًا عند الحد نفسه.
- المصدر عند الانتظار: `source_expires_at = document_created_at + 24h`؛ لا يمدد
  العرض أو إعادة الطلب المهلة. بعد الانتهاء يمنع التنفيذ وتتاح حالة تشغيل خالية من
  المحتوى حتى نهاية عمر سجلها؛ يلزم اختيار تمثيل EXPIRED المتوافق مع الحالات الحالية.
- المصدر عند النجاح/الفشل/الإلغاء: حذفه المنطقي وتغيير الحالة ضمن عملية موثوقة، مع
  إزالة المؤشرات والمراجع غير اللازمة وإبطال caches؛ لا ضمان لتصفير كل ذاكرة العملية.
- التقرير: `artifact_expires_at = artifact_created_at + 7d`؛ يحتاج توقيت إنشاء فعليًا
  جديدًا، ولا يعاد توليده لمجرد تكرار execute بعد انتهاء صلاحيته.
- سجل المهمة: المقترح `record_expires_at = document_created_at + 30d`؛ **نقطة بدء
  الثلاثين يومًا قرار معروض للاعتماد** لأن الطلب الأصلي لم يحسم البداية.
- سجل مسموح فقط: معرّف مولد، version للسياسة، حالات وتوقيتات وأسباب تشغيل عامة
  وعلامات إزالة المحتوى. لا نص/تقرير/مقتطف/اسم أصلي/رمز. الاحتفاظ بالإحصاءات أو
  البصمة بعد حذف التقرير يحتاج غرضًا واضحًا؛ الافتراضي المقترح إسقاط غير الضروري.
- RUNNING المتروكة بعد crash: لا تُعتبر ناجحة ولا تُعاد آثارها تلقائيًا؛ **BLOCKED
  تصميمًا** حتى اعتماد حد زمني للتعافي يضمن عدم حفظ المصدر إلى الأبد.

### 7.2 المنع والتنظيف

اقتراح يحتاج الاعتماد: رفض execute/المحتوى المنتهي بـ410، مع بقاء 404 للمجهول أو غير
المتاح دون كشف بيانات. GET الحالة المنقّحة قد يبقى حتى 30d؛ المصادقة تسبق الإفصاح.
كل مسارات المحتوى، ومنها JSON والقوائم، يجب أن تتفق على المنع، لا route واحد فقط.

اقتراح آلية بدون خدمة إضافية: sweep عند بدء التطبيق قبل إتاحة المحتوى، ومجدول داخل
العملية الواحدة بفاصل لا يتجاوز 60 ثانية أثناء التشغيل، مع فحص TTL عند كل وصول.
المنع يبدأ عند الموعد نفسه ولو تأخر sweep. الحذف المنطقي المستهدف خلال دورة التنظيف
التالية؛ عند تعطل التطبيق لا يوجد تنفيذ سحري عند الموعد، ويُستكمل عند عودته. فشل
التنظيف يُسجل كسبب عام ويُعاد بمحدودية؛ لا تُعلن علامة DELETED قبل نجاح الكتابة.
فاصل 60 ثانية و410 مقترحان لا إعدادان حاليان.

ينبغي أن تكون إزالة المصدر/التقرير وإصلاح الحالة قابلة للتكرار وذات نطاق document
واضح، وأن تشمل Artifacts اليتيمة حتى إن غاب مؤشرها من الحالة. ثم بعد 30d تزال الحالة
وملخصها وأحداثها وارتباطاتها، دون المساس بمهام الوكيل الأخرى. لا تضاف قاعدة ثانية.

### 7.3 حد المحتوى 100 MiB

- القيمة الافتراضية المقترحة: **104,857,600 بايت**، قابلة للضبط بعد اعتماد طريقة الإعداد.
- العد المنطقي: مجموع بايتات UTF-8 للمصادر المحفوظة + بايتات تقارير المستندات
  المحفوظة، بما فيها Artifacts يتيمة ما زالت موجودة. استعمل المحتوى الفعلي لا ثقة
  عمياء في size_bytes وحدها؛ يتجاوز التقرير المنتهي العد فقط بعد إتمام الحذف.
- لا تدخل الأسماء والـhashes مرتين في حساب المحتوى. JSON overhead وrun_meta وWAL
  والنسخ الاحتياطية وRAM ليست مشمولة؛ **ليس حدًا إجماليًا لحجم القرص أو حماية من
  امتلائه**. يلزم رصد المساحة الفعلية وسياسة منفصلة لفشل القرص.
- عند بلوغ الحد يُرفض الرفع الجديد برسالة واضحة؛ إن أضاف الملف تجاوزًا يرفض قبل
  الحفظ. لا تُحذف بيانات ما زالت ضمن فترة الاحتفاظ لفتح مكان تلقائيًا.
- يلزم حجز/حساب ذري ضمن عملية واحدة لمنع تجاوز متزامن، وسياسة لمساحة التقرير قبل
  بدء توليده. رد الخطأ وآلية حجز الناتج **BLOCKED تصميمًا حتى الاعتماد**؛ لا تكلفة
  مالية بديلة ولا انتقال إلى تخزين مدفوع.

### 7.4 النسخ الاحتياطية والمستندات القديمة

لا توجد آلية backup للمستندات يديرها مسار MVP-0 المفحوص. نسخ النظام والمشغّل والمنصة
والمستخدم والمزامنة خارج ضمان التطبيق؛ وجودها ومددها **NOT VERIFIED**. لا يُستنتج
أنها غير موجودة. قبل استعادة نسخة قديمة مستقبلًا يجب تطبيق السياسة المعتمدة قبل فتح
أي وصول للمحتوى، وإلا تعود بيانات سبق انتهاء صلاحيتها.

للسجلات القديمة بلا توقيت إنشاء Artifact: لا تعطِ 7 أيام جديدة صامتة من أول تشغيل.
اختر قبل التنفيذ بين تصنيفها غير متاحة لحين مراجعة أو احتساب محافظ من توقيت المهمة
بقرار معلن. لا تُعدَّل الملفات القديمة التي رُصدت أثناء هذا الفحص.

## 8. SQLite وsecure_delete وWAL: ما نعرفه وما لا نضمنه

**VERIFIED — code:** المُنشئ يطلب WAL وsynchronous=NORMAL، لكنه لا يضبط secure_delete
ولا retention ولا checkpoint يدويًا ولا VACUUM. لا يجوز الاستدلال من عدم ضبط
secure_delete أنه OFF؛ قد يتأثر الافتراضي بالبناء/الإعداد. نجاح PRAGMA journal_mode
الفعلية وقيمة secure_delete على اتصال تطبيق حقيقي **NOT VERIFIED** لأننا لم نفتحه.
إصدار مكتبة Python المحلي، دون أي اتصال DB، هو **SQLite 3.40.1**.

رُوجع مصدر SQLite الرسمي عبر GitHub للإصدار نفسه:

- [pragma.c — version-3.40.1](https://github.com/sqlite/sqlite/blob/version-3.40.1/src/pragma.c):
  secure_delete يقبل query وOFF/ON/FAST، ويحوّل FAST إلى قيمة منفصلة.
- [btree.c — version-3.40.1](https://github.com/sqlite/sqlite/blob/version-3.40.1/src/btree.c):
  تعليق ودالة sqlite3BtreeSecureDelete يصفان الكتابة بالأصفار، وأن FAST لا يمسح
  كل محتوى freelist المحذوف؛ لا يُعامل بديلًا مكافئًا لـON.
- [wal.c — version-3.40.1](https://github.com/sqlite/sqlite/blob/version-3.40.1/src/wal.c):
  WAL يسجل صفحات متعددة عبر معاملات؛ checkpoint ينقلها إلى DB، وقد تبقى frames قديمة.

هذا تحقق من دلالة المصدر، لا تجربة بايتات للقاعدة المحلية. مراجع المتابعة الرسمية:
[PRAGMA secure_delete](https://sqlite.org/pragma.html#pragma_secure_delete)،
[WAL](https://sqlite.org/wal.html)، [VACUUM](https://sqlite.org/lang_vacuum.html).
روابط sqlite.org ليست دليل تجربة أُجريت هنا؛ لم يُجلب محتواها مباشرة في هذه الجولة.

قبل أي تنفيذ لاحق، في قاعدة **اختبار اصطناعية منفصلة فقط**: اقرأ الإعدادات الفعلية
وcompile options، ثم اختبر ON قبل عمليات التغيير/الحذف مع مدخلات فريدة، والـWAL
والقراء المفتوحين، وإعادة الفتح وفشل التخزين. إن اقتُرح checkpoint/truncate أو
VACUUM، تُحدد شروط السلامة والأقفال والمساحة والنسخ الناتجة والتفويض أولًا. لا يُحذف
WAL/SHM يدويًا أثناء الاستخدام، ولا تُجرى صيانة تلقائية على قاعدة مستخدم قبل اعتمادها.

الحذف المنطقي ≠ تنظيف صفحات حية ≠ اختفاء البايتات من كل وسيط. حتى بعد تجربة لا تجد
النص في DB/WAL الحاليين، يبقى ضمان المحو الجنائي من SSD/نظام ملفات COW/لقطات/نسخ
احتياطية أو swap **BLOCKED كضمان شامل**. SHA-256 ليس تشفيرًا أو إخفاءً للمحتوى، ولا
يزيل هذا الحد.

## 9. أصغر اتجاه تنفيذ ممكن بعد الاعتماد — لا تغييرات في هذه الجولة

**يمكن إبقاء سجل المهمة عند إزالة المحتوى** لأن المصدر داخل metadata والتقرير في
صف مستقل؛ لا حاجة مثبتة إلى قاعدة ثانية. لكن العقد الحالي لا يدعم حذف Artifacts
أو المهام؛ مجرد pop من metadata لا يزيل التقرير. المقترح تمديد RunStore بعمليات
محدودة للمستندات ومعاملة حذف/تحديث موثوقة، أو capability صريحة يرفض غيابها تشغيل
ميزة التنظيف؛ لا fallback صامت مع بقية backends.

نطاق مرشح للتغيير لاحقًا، وليس تفويضًا: storage.py للمخزن والحذف/الحصة؛ documents.py
للمهل والحالات وتوقيتات Artifact؛ runtime.py لإبطال cache والمنع المشترك؛ app.py و
cela.py لضمان عدم تجاوز المسارات المشتركة؛ إعداد logging/نقل اسم الملف لمنع حفظه؛
واجهة المستندات لتفسير الانتهاء والإلغاء دون إعادة إنشاء تقرير. تُضاف اختبارات
الذاكرة وSQLite والتوافق مع `/runs`، ولا تُعدّل مسارات وكلاء أخرى لإجبارها على النجاح.

### بوابات تحقق التنفيذ المطلوبة لاحقًا — جميعها NOT VERIFIED الآن

1. ساعة قابلة للحقن؛ الحدود قبل الموعد وعنده وبعده لـ24h/7d/30d؛ بلا sleep طويل.
2. pending منتهية لا تنفذ بعد إعادة التشغيل؛ التقرير المنتهي لا يصل عبر download
   أو JSON العام أو قائمة/استرجاع السطح الخاص أو cache قديم.
3. حذف المصدر في النجاح والفشل والإلغاء؛ فشل بين save_artifact وsave_state لا يترك
   محتوى يتيمًا خارج الجرد. فشل الصيانة لا يسجّل نجاح حذف كاذبًا.
4. بعد 7d: غياب محتوى التقرير من جميع طبقات المخزن، وبقاء سجل تشغيلي خالٍ من النص
   حتى 30d. بعد 30d: غياب السجل وارتباطاته من DB/get/list/cache دون إتلاف مهام أخرى.
5. تحميل snapshot قبل التنفيذ ثم تنظيف المصدر؛ لا تُبقي runtime.states نسخة قديمة
   ولا تعيدها إلى القرص. فحص InMemory وSQLite كلٌّ على حدة.
6. حدود 100 MiB وحجز التقرير والتزامن المحدود داخل عملية واحدة؛ عدم حذف ملفات ضمن
   مهلة الاحتفاظ؛ رفض آمن لفشل القرص دون اتصال خارجي.
7. أسماء ملفات اصطناعية ورموز وهمية لا تظهر في logs؛ لا source أو مقتطف في سجل حذف؛
   حماية ملفات السجلات الخارجية قرار تشغيل منفصل.
8. اختبار SQLite اصطناعي للـsecure_delete/WAL منفصل عن قبول الحذف المنطقي، ونتيجة
   صريحة لما لم يُختبر. لا ادعاء فحص جنائي شامل.
9. اختبارات عقود `/runs` وArtifacts للمهام غير المستندية تظل ناجحة؛ اختبارات المتصفح
   الموثقة تُعاد بعد أي تغيير في الحالات أو الاستجابات.

## 10. القرارات المعلّقة وشرط إغلاق مرحلة الفحص

**الجرد والتوثيق مكتملان في نطاق الكود والمسارات وmetadata الملفات المذكورة.** محتويات
القاعدة الفعلية وإعداداتها والنسخ الخارجية لم تُفحص، والحذف ليس منفذًا ولا مختبرًا.

قبل الترخيص بالتنفيذ يلزم اعتماد: 24h/7d/30d وبدء الثلاثين يومًا، تمثيل EXPIRED ورد
الانتهاء، الإلغاء وتعافي RUNNING، طريقة توقيت السجلات القديمة، دورية التنظيف، سلوك
امتلاء الحصة ومساحة التقرير، ونطاق صيانة SQLite والتعامل مع سجلات الوصول الخارجية.

**NEXT: انتظار اعتماد عقد التنفيذ؛ لا تغيير سلوك الحذف أو إعدادات SQLite أو بيانات
المستخدم بناءً على هذه الوثيقة وحدها.**
