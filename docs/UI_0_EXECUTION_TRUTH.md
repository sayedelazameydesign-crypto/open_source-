# UI-0 — تثبيت خط الأساس وصدق العرض

## الحالة

**IMPLEMENTED / VERIFIED LOCALLY** للمتطلبات أدناه، لا جاهزية إنتاجية ولا اكتمال
الواجهة الجديدة. الفرع `arena/b25f704f-open-source`؛ الأساس `14db8a3` مع تعديلات
MVP-0 السابقة التي حُفظت. لا commit أو push أو نشر أو تغيير فوترة، ولا سياسة حذف
أو تغيير لقواعد مستخدم قديمة. المعاينة الحالية على 3000 وخلفيتها على 8080 بوضع
تجريبي ومخزن `memory://` وسجل نتائج معطل، كما كانت عند استئنافها.

## السبب الجذري والإصلاح

كان فرع `serve` في CLI ينشئ `build_demo_platform(mode="flow")` مرة واحدة. يحوّل
`single_platform_factory` وضع هذه المنصة إلى ReAct عند الطلب، لكنه لا يبدل نموذج
التخطيط. أول استجابة لذلك النموذج مصفوفة JSON بلا tool_calls؛ فيعدها ReAct جوابًا
نهائيًا ويغلق الدورة. هذا يفسر الخطة الخام في تجربة المستخدم، وليس مشكلة تنسيق JSON.

الآن CLI يمرر مصنع منصات جديدة حسب الوضع والحد الأقصى للخطوات؛ ويحل Runtime وضع
`auto` قبل اختيار منصة ذلك الوضع. لا تبدأ المهمة مرتين. لا يُخفى JSON ولا تتحول خطة
نموذج إلى استدعاءات أدوات عبر تخمين الواجهة. دعم تمرير Platform جاهزة إلى API
يبقى قائمًا للتوافق؛ من يفعل ذلك مسؤول عن توفير النموذج المناسب لوضعه، وليس هناك
وعد بتبديل أي نموذج مخصص تلقائيًا.

اختبار مستقل يعيد إنتاج **التوصيل القديم عمدًا**، ثم اختبارات أخرى تثبت التوصيل
الصحيح لـreact/flow/auto وعزل كائنات المنصات. وجود اختبار يعيد إنتاج السلوك القديم
ليس معناه أن CLI ما زال يستعمله.

### إخفاق أداة أثناء فحص المتصفح

رُصدت أثناء التشغيل الحي نتيجة python_execute غير ناجحة بسبب قيود تشغيل unshare
في هذه البيئة. لم تُخفف قيود العزل. كان النص التجريبي القديم يكرر الجواب العددي حتى
عند الخطأ؛ عُدّل لعدم تأكيد الحساب ما لم تتضمن ملاحظة الأداة الناتج المتوقع. نص
التلخيص التجريبي في flow لم يعد يزعم إثبات تصفح موقع فعلي.

في الجولة المصورة الأخيرة: نتيجة أداة مسجلة واحدة، صفر ناجح، واحدة غير ناجحة.
الواجهة تعرض هذا التحذير، وخرج المنفذ يصرح بأن الحساب غير متحقق. تظل حالة المحرك
`completed` لأن دورة النص انتهت؛ **لا تُعلن المهمة الأصلية ناجحة بسبب ذلك**. الاختبارات
البرمجية للحساب اجتازت في بيئتها، لكن هذا لا يستبدل نتيجة الأداة الفاشلة في المتصفح.

## عقود إضافية متوافقة

لا تغيير في الطلبات القائمة أو أسماء الحالات أو صحة الخدمة العامة. الإضافات:

- `GET /runtime-info`: محمي بمصادقة المنصة؛ يصف **إعداد المنفذ المرجعي**، وليس
  تاريخ مهمة قديمة أو إثبات اتصال بمزود.
- لقطات المهمة تحمل `execution` و`recorded_tool_results` و`tool_results_summary`.
- `execution.kind`: `scripted` أو `provider_adapter` أو `unknown`.
- `execution.model_name`: اسم المنفذ العام، لا عنوان خدمة أو مفتاح API.
- `execution.goal_verification`: `not_verified` حاليًا؛ لا مقيم مستقل للهدف في UI-0.
- `tool_results_summary`: أعداد المسجل/الناجح/غير الناجح؛ نجاح أداة لا يثبت نجاح الطلب.
- يحفظ RunState الوصف مع المهمة؛ اللقطات القديمة بلا الوصف تظل `unknown` بدل
  إسقاط إعداد المنصة الحالية عليها. لا ترحيل لمخطط SQLite.
- اسم Qwen في ModelRouter **وجهة توجيه مقترحة**؛ لا يدل وحده على استدعاء Qwen.
  وصف `provider_adapter` يعني إعداد موصل، لا تحققًا مستقلًا من هوية المزود.

## تغييرات الواجهة

- إفصاح دائم عن المحاكاة والمنفذ؛ انتظار/غياب metadata يبقى غير متحقق.
- «خرج المنفذ» بدل اعتباره جوابًا نهائيًا موثوقًا، وتحذير عند نتائج أدوات غير ناجحة.
- فصل انتهاء البث عن حالة المحرك والتحقق من الهدف.
- عدم تحويل إلغاء اتصال قديم عند بدء مهمة أخرى إلى خطأ اتصال كاذب.
- مسح لقطة المهمة السابقة عند البدء وتجاهل ردود اللقطات المتأخرة لمهمة أخرى.
- إزالة مؤقت polling المكرر؛ بقاء مؤقت fallback واحد.
- تعريف معالجة TXT بأنها «محلية حتمية — بلا نموذج»؛ لا تعديل لمعالجتها أو الاحتفاظ.

هذا ليس إعادة تصميم الشريط الجانبي أو الهاتف أو نظام الملفات؛ تلك مراحل لاحقة.
