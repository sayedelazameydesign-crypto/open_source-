# خطة توحيد CELA إلى نظام واحد متكامل

> **الحالة:** خطة مقترحة — لا تعني أن البنود أدناه نُفّذت.
> **التاريخ:** 2026-10-20

## 1. القرار المعماري

المقصود بـ«نظام واحد» هو **منتج واحد، ومسار تشغيل واحد، وعقد API وهوية وسياسات وبيانات موحّدة**؛ وليس دمج كل الشيفرة في حزمة ضخمة. تُحافَظ على حزم `os_*` وحدودها الحالية، ويكون التكامل عبر عقود واضحة.

الواجهة والـAPI والخلفية المقترحة:

```text
Next.js Workspace (عربي/إنجليزي، RTL، تشغيل وموافقات وArtifacts)
        │
        ▼
BFF / جلسة المشغّل (الأسرار لا تصل إلى المتصفح)
        │
        ▼
os_server — API موحّدة ومصادقة وحدود طلبات
        │
        ▼
ApiRuntime — إدارة التشغيلات والموافقات والبث
        │
        ├── Platform: ReAct / PlanningFlow / ميزانيات / ModelRouter فعلي
        ├── ToolRegistry: أدوات المنصة والتكاملات المصرّح بها
        └── RunStore: حالة التشغيل والأحداث والنتائج والملفات
                 │
                 ├── PostgreSQL: مصدر البيانات الدائم في الإنتاج
                 ├── Redis: أحداث مباشرة وطوابير وتذاكر قصيرة العمر
                 └── تخزين ملفات: Artifacts الكبيرة عند الحاجة
```

### قرارات التوحيد

1. `packages/os_server` و`os_orchestration.Platform` هما مسار التنفيذ الوحيد؛ لا تشغّل الواجهات محركات وكلاء أو عملاء نماذج منفصلة.
2. `packages/web` هي واجهة المنتج الأساسية. تتحول `cela_pro_app.py` تدريجيًا إلى واجهة متوافقة مع الـAPI، ثم تُوقَف كمسار تنفيذ مستقل بعد اكتمال تكافؤ الميزات.
3. تُنقل محادثة CELA.PRO، واختبار المزوّد، ومكتبة الأبحاث، واستيراد المهارات إلى واجهات وخدمات المنصة نفسها؛ لا تنشئ مخازن أو حواجز موازية.
4. يبقى `packages/craft-launcher` طرفًا ثالثًا معزولًا كما هو؛ التكامل عبر `os_launcher` فقط، دون تعديل الشجرة المُضافة أو تجاوز قيود ترخيصها.
5. تُراجع `packages/legacy` وتُعزل واجهاته، ثم تُزال فقط بعد إثبات عدم وجود مستهلكين. لا يُحذف أي مسار قبل توفر بديل واختبار ترحيل.
6. يُختار عقد API مُصدّر واحد بإصدار واضح. الاقتراح هو توسيع `/cela/v1` ليغطي وظائف المنصة؛ تبقى `/runs` و`/api/*` كواجهات توافق مؤقتة، ثم تُوقَف وفق سياسة إصدار معلنة.

## 2. النطاق المستهدف

- **تشغيل موحّد:** كل مهمة — من الواجهة أو CLI أو عميل API — تمرّ عبر `Platform.run`، وتحصل على `run_id` وميزانية وأحداث وسجل نتيجة موحّد.
- **توجيه نماذج حقيقي:** سجل مزوّدين يربط أدوار `planner` و`fast` و`vision` و`critic` بنماذج قابلة للاستدعاء. حدث `model_selected` يجب أن يصف النموذج الذي أُرسل إليه الطلب فعلًا، لا مجرد اختيار حسابي.
- **تكاملات كإضافات:** Reach وMCP وIndigo وWAAPI وLauncher وحدات اختيارية لها عقد موحّد، وصلاحيات معلنة (شبكة، ملفات، تنفيذ عملية)، وتفعيل صريح افتراضيًا مغلق.
- **نطاق بيانات:** كل تشغيل وArtifact وذاكرة ومهارة ومعرفة مرتبط بـ`workspace_id`، وبـ`principal_id` عند تفعيل تعدد المستخدمين.
- **تشغيل محلي ونشر واحد:** SQLite للتطوير المحلي فقط؛ PostgreSQL/Redis والخدمات المساندة تُدار عبر إعدادات وتشخيص موحّدين للإنتاج.

> **قرار منتج مطلوب قبل مرحلة الهوية:** هل النسخة الأولى لمشغّل واحد أم خدمة متعددة العملاء؟ الخطة توصي بإطلاق أولي لمشغّل/مساحة عمل واحدة، لكن إضافة `workspace_id` وعزل السجلات من البداية تمنع إعادة تصميم مؤلمة لاحقًا. لا يُسوّق النظام كخدمة متعددة العملاء قبل إنجاز العزل والملكية والحصص.

## 3. مراحل التنفيذ وبوابات القبول

### المرحلة 0 — تثبيت النطاق والعقود

**العمل**
- جرد الوظائف الموجودة في `packages/os_*` و`packages/web` و`cela_pro_app.py` و`packages/legacy`، وتصنيف كل وظيفة إلى: تُدمج، تُبقى إضافة اختيارية، تُرحّل، أو تُوقف.
- كتابة ADR واحد يثبت: الواجهة الأساسية، عقد API، نموذج الهوية، مصدر الحقيقة للبيانات، وحدود ثقة الإضافات.
- حصر متغيرات البيئة والأسرار والإعدادات في مرجع واحد، وتحديد قيم التطوير والإنتاج دون تكرار منطق التهيئة.

**بوابة الخروج**
- جدول تكافؤ ميزات بين CELA.PRO والواجهة الأساسية.
- قائمة مسارات API التي ستبقى للتوافق، وموعد/سياسة إيقافها.
- خريطة بيانات وترحيل قابلة للاختبار مع نسخة احتياطية وخطة تراجع.

### المرحلة 1 — إغلاق المخاطر التي تمنع التوحيد الآمن

**العمل**
- إصلاح حد SSRF: فحص DNS وتثبيت العنوان العام المسموح عند الاتصال نفسه، لا الاكتفاء بفحص سابق؛ إعادة الفحص لكل تحويلة، وإضافة اختبار يحاكي تغيّر DNS بين الفحص والاتصال. تقييد wildcard في قنوات Reach وMission عند النشر العام.
- فرض حدود حقيقية على PlanningFlow: حد أقصى للخطة، والخطوات وإعادات التخطيط والتوازي، وسقوف وقت/توكنز؛ استدعاء فحص الميزانية قبل كل دفعة وقبل التخطيط والتركيب النهائي.
- تقييد مدخلات API، ومنها `max_steps` وحجم المهمة ومعدل إنشاء التشغيلات، وإرجاع أخطاء واضحة عند تجاوز السقف.
- جعل تنفيذ الكود غير الموثوق معطّلًا افتراضيًا خارج التطوير المحلي، وعدم اعتباره معزولًا إلا إذا تحققت خلفية microVM/خدمة sandbox فعلية. فشل التهيئة يعني الرفض، لا الرجوع الصامت إلى subprocess محلي.
- إبقاء MCP `stdio` وReach CLI مغلقين افتراضيًا، ونقل تشغيلهما — عند الحاجة — إلى عامل معزول بصلاحيات أقل.

**بوابة الخروج**
- اختبارات تثبت رفض الوصول الداخلي عند DNS عادي وعند إعادة الربط وعبر التحويلات.
- اختبارات Flow تثبت أن الحدّ لا يمكن تجاوزه حتى لو أعاد النموذج خطة ضخمة أو استهلك زمنًا طويلًا.
- لا يوجد نشر عام يسمح بتنفيذ كود على المضيف أو يعلن عزل شبكة غير متحقق.

### المرحلة 2 — توحيد المحرك والتوجيه

**العمل**
- إنشاء واجهة `ModelProviderRegistry` أو ما يعادلها، مع مزوّد فعلي لكل دور، ومهلات وإعادة محاولة وسياسة fallback معلنة.
- تمرير الاختيار إلى العميل الفعلي في ReAct وFlow والمراجع؛ تسجيل `model_id` الفعلي، وقياس الاستخدام من ردّ المزوّد. لا يُعرض تقدير التكلفة كفاتورة فعلية.
- نقل `OrionAgent` و`SkillEngine` من المسار المنفصل إلى خدمات/عقود داخل المنصة، وإعادة استخدام `ToolRegistry` وGuardrails وBudget وRunLedger.
- توحيد إظهار حالات fallback؛ إذا تحوّل التنفيذ من مزوّد حي إلى scripted، يظهر ذلك للمستخدم وسجل التشغيل بوضوح.

**بوابة الخروج**
- اختبار تكاملي يثبت أن مهمة `planner` ترسل `model_id` الخاص بالمخطط، ومهمة `fast` ترسل نموذج السرعة، وأن حدث الواجهة يطابق الطلب الفعلي.
- كل واجهة تُنشئ التشغيل عبر `ApiRuntime` فقط؛ لا توجد حلقة وكيل بديلة داخل Gradio.

### المرحلة 3 — هوية وبيانات وتشغيل مستمر

**العمل**
- اعتماد principal/workspace في سياق الطلب، وتسجيل مالك التشغيل وفحص الملكية عند القراءة والبث والموافقة وجلب Artifacts.
- الاحتفاظ برمز خدمة للمشغّل والتكاملات الآلية، واستخدام جلسة BFF للواجهة. تُحدد الأدوار والصلاحيات بوضوح، ولا تُرسل مفاتيح المزوّد إلى المتصفح.
- اعتماد PostgreSQL مصدرًا دائمًا في الإنتاج، وRedis للأحداث الحية/التذاكر والطوابير، وتخزين ملفات منفصل عند كبر Artifacts. SQLite يبقى مسار تطوير.
- نقل سجل JSONL إلى واجهة تخزين موحّدة، مع تدوير ومدة احتفاظ وحذف قابل للتدقيق. إضافة سياسات احتفاظ للرسائل والأحداث والملفات والذاكرة.
- فصل تنفيذ المهام عن عملية HTTP بعامل/طابور، وربط أحداث Redis بمؤشر تسلسلي يصدر من مصدر مشترك، حتى يعمل البث والاستئناف عبر أكثر من نسخة.
- ترحيل بيانات CELA.PRO والذاكرة والمهارات إلى مخازن موحّدة مع فضاءات معزولة، واختبار الاستعادة قبل تبديل القراءة والكتابة.

**بوابة الخروج**
- CI أو بيئة قبول تشغّل PostgreSQL وRedis حقيقيين، لا بدائل وهمية فقط.
- تشغيل بدأ في نسخة خادم يمكن قراءته ومتابعته والموافقة عليه من نسخة أخرى، ويستمر بعد إعادة تشغيل API وفق سياسة الاستعادة.
- اختبار سلبي يثبت عدم قراءة مستخدم/مساحة عمل بيانات مستخدم/مساحة أخرى.

### المرحلة 4 — توحيد تجربة المستخدم وترحيل CELA.PRO

**العمل**
- جعل مساحة Next.js واجهة واحدة: المهام، المحادثة، الموافقات، الحالة، السجل، الذاكرة والمعرفة والمهارات والتكاملات.
- نقل ميزات CELA.PRO: اختيار إعداد مزوّد مسموح، اختبار اتصال إداري، محادثة عربية RTL، مكتبة الأبحاث، واستيراد `SKILL.md`.
- يقتصر إعداد المزوّد على المشغّل؛ مفاتيح API تُقرأ من مخزن أسرار الخادم، ولا يرسلها المتصفح ولا يختار المستخدم عنوانًا عشوائيًا.
- إكمال معاينة Artifacts وشجرة DAG، وعرض نموذج التنفيذ الفعلي، والميزانية، وسبب الرفض/fallback.
- إبقاء Gradio مؤقتًا كعميل للـAPI الموحد إن لزم، ثم إيقافه بعد اكتمال التكافؤ والتحقق من عدم وجود مستهلكين.

**بوابة الخروج**
- قائمة تكافؤ ميزات مكتملة، واختبارات واجهة/متصفح للمسارات الحرجة بالعربية والإنجليزية.
- لا يُجري أي مسار في CELA.PRO اتصال مزوّد أو كتابة ذاكرة مباشرة خارج خدمات المنصة.

### المرحلة 5 — توحيد الإضافات والنشر

**العمل**
- تعريف عقد إضافة موحّد: حالة، إعداد، صلاحيات، فحص صحة، مهلة، تدقيق، وإغلاق منظم.
- ربط Reach وMCP وIndigo وWAAPI وLauncher بالعقد نفسه؛ تظل الإضافات اختيارية ومغلقة افتراضيًا، ولا تحصل الإضافة على صلاحية لا تحتاجها.
- اعتماد `os_server.app:create_app` كـfactory canonical؛ يبقى `deploy/g1a/main.py` wrapperًا رفيعًا يعرّف `app = create_app()` لمدخل Docker/ASGI.
- فرض بوابة نشر fail-closed قبل أي adapter: يفحص **إعداد الهدف نفسه** ويشترط `CELA_CODE_EXEC_MODE=disabled`؛ عند الغياب يرفض النشر ولا يتجاوز الشرط ولا يختار provider بديلًا.
- مسار artifact واحد لكل provider: Render يستخدم Blueprint بعد إصلاحه؛ بقية providers تستخدم Docker image منشورة إلى GHCR بمدخل `deploy/g1a`، دون تبديل artifact ضمني.
- تثبيت Python على خط 3.11/3.12 بين Render وDocker. إعداد API probe افتراضيه HTTPS/443 و`*.onrender.com`، مع DNS pinning وEgressPolicy و`trust_env=False` ورفض redirects؛ allowlist نشر الويب منفصلة (`*.pages.dev`, `*.vercel.app`, `*.netlify.app`)، وprovider API hosts تُضاف مع adapter بعد التحقق فقط.
- فصل فحص اتصال PostgreSQL عن HTTP probe؛ Postgres مطلوب لحفظ التشغيلات عبر إعادة تشغيل الخدمة، خصوصًا Render Free.
- إضافة اختبار قبول حي للمزوّد، وقاعدة البيانات، وRedis، ومسار الواجهة؛ مع فصل الاختبارات الحية عن CI السريع دون الادعاء أنها نُفذت إذا لم تعمل.

**بوابة الخروج**
- نشر قابل لإعادة الإنتاج، وفحص بعد النشر، وخطة rollback مجرّبة، وسجل يوضح إصدار التطبيق وإعداد التنفيذ دون كشف أسرار.

### المرحلة 6 — قطع الانتقال والإصدار

- تشغيل الواجهة الموحدة أولًا على بيئة قبول، ثم نقل قاعدة البيانات تدريجيًا مع مقارنة الأعداد والبصمات.
- تحويل العملاء إلى عقد API الموحد، ومراقبة استخدام المسارات القديمة، ثم تعطيلها بعد فترة توافق معلنة.
- إيقاف تطبيق Gradio المستقل بعد تحقق تكافؤ الوظائف؛ لا يُحذف مصدره قبل حفظ تاريخ/خطة إزالة واضحة.
- عدم إعلان جاهزية إنتاج أو إصدار `1.0` قبل إغلاق بوابات الأمن، الميزانية، تعدد النسخ، وجودة النماذج.

## 4. معايير القبول النهائية

يُعدّ التوحيد مكتملًا عندما تتحقق جميع النقاط التالية:

1. **مسار تنفيذ واحد:** كل واجهة وCLI يمر عبر `Platform` و`ApiRuntime`، ويملك كل تشغيل معرّفًا وسجلًا ومالكًا واضحًا.
2. **توجيه صادق:** النموذج المسجل هو النموذج الذي استقبل الطلب فعلًا، مع إظهار fallback والاستخدام الحقيقي.
3. **حدود تكلفة قابلة للإنفاذ:** حدود الخطوات والخطة والوقت والتوكنز والتوازي تعمل في ReAct وFlow وAPI.
4. **حماية شبكة فعلية:** منع IP داخلي/metadata على مستوى الاتصال، واختبار DNS rebinding والتحويلات؛ سياسات واضحة لقنوات CLI وMCP.
5. **عزل تنفيذ فعلي:** لا تنفيذ غير موثوق على المضيف في إعداد الإنتاج؛ الاختيار الافتراضي fail-closed.
6. **عزل بيانات:** لا وصول عابرًا للمساحات أو المستخدمين؛ ملكية وفحص صلاحيات عند كل قراءة وموافقة وArtifact.
7. **استمرارية:** تشغيلات وأحداث وملفات قابلة للاستعادة؛ اختبارات حية لـPostgres/Redis وعبر نسختين.
8. **واجهة موحدة:** CELA.PRO لا ينفذ منطقًا موازيًا، والـArtifacts وDAG والموافقات ظاهرة في الواجهة الأساسية.
9. **أدلة حديثة:** أرقام الاختبارات تعني بوضوح «مجمّعة» أو «منفّذة»، ونتائج الاختبار الحي والـbenchmarks مؤرخة وقابلة لإعادة الإنتاج.

## 5. ترتيب الأولوية

**قبل أي إطلاق عام:** المرحلة 1، ثم اختيار نموذج الهوية في المرحلة 3.

**قبل دمج واجهات CELA.PRO:** المرحلة 2، ثم توفير APIs وبيانات موحّدة في المرحلتين 3 و4.

**قبل التوسع أو إعلان الإنتاج:** اختبارات قاعدة البيانات/Redis الحية، وعامل التنفيذ، وتدقيق عزل البيانات والشبكة، ومعايير قبول المرحلة 6.

> هذه الخطة تتعمد ترتيب **ضمانات التنفيذ والبيانات قبل تجميل الواجهة**؛ توحيد شكل التطبيق وحده لا يجعل النظام متكاملًا أو آمنًا.
